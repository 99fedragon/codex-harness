# 웹 앱

- 시작: 루트의 main/skeleton/webapp 이 있으면 product/app 으로 복사해 거기서 시작한다 (「기능 한 칸 더하는 법」 은 그 README). 없으면 FastAPI 와 SQLite, 화면은 서버가 주는 HTML 과 JS 한 벌. 묻지 말고 고른다
- 첫 30분 안에 빈 앱으로 미리보기 점검: 서버를 띄우고 `check_preview.py` (로그인 → 토큰으로 요청 → 다시 요청) 가 통과하는지. 미리보기 창에서 사람이 로그인 → 새로고침 → 유지를 한 번 본다
- 큰 틀 (메인의 「큰 틀」 전달문, 사람이 요구 표를 확인한 직후): 뼈대 위에 요구.md 가운데 모르는 곳에 걸리지 않는 것을 요구 번호로 전부 만든다. 자료 구조와 데이터셋 검증과 적용, 역할과 로그인, 핵심 대상의 화면 (목록, 상세, 만들기), README 흐름의 기본 꼴과 적힌 운영 규칙, 내보내기, 헬스체크, Dockerfile, 제출 파일 초안. 모르는 곳에 걸린 규칙과 값은 한곳 (설정이나 규칙 모듈) 에 자리만 두고 가장 단순한 기본값으로 돌게 한다 (코드가 그 값을 읽어, 값만 바꾸면 동작이 바뀌게). README 밖 기능은 넣지 않는다 (담당자 말은 합의 뒤에). 끝난 조건: 화면에서 핵심 흐름이 처음부터 끝까지 한 번 돌고 요구 번호마다 시험 (없으면 「모르는 곳 U번호 대기」). 팀원을 쓸지와 몇은 팀장이 정한다
- 로그인은 토큰 방식 (로그인 응답의 토큰을 요청 머리 Authorization 에 싣는다). 쿠키 세션을 쓰지 않는다 (미리보기 창이 다른 도메인 안에 뜨면 쿠키가 제3자 쿠키가 되어 안 보내진다). 쿠키를 꼭 써야 하면 SameSite=None 과 Secure 를 묻고 정한다. CSRF 검사는 쿠키 세션일 때만
- 막히면 가른다: 같은 요청을 curl 로 토큰이나 쿠키를 이어 보내 되면 서버는 맞고 브라우저 정책 문제
- 새 창, 팝업, alert, confirm, target=_blank, 파일 선택창과 저장창을 쓰지 않는다 (화면 안의 대화상자와 글로). 내보내기는 화면에 JSON 을 보이고 복사하게 한다
- 상태를 바꾸는 단추는 누른 뒤 서버에서 다시 읽어 그린다 (화면의 값을 믿지 않는다). 하기 → 취소 → 다시 하기 되풀이를 시험에 넣는다
- 기능이 셋 넘으면 탭 (한 탭 한 기능). 꼴은 theme.css 한 벌로 통일. 「회사 스타일로」 를 받으면 research 가 넘긴 자산.md 의 색과 글꼴로 theme.css 만 바꾼다. 로고 그림은 받지 않는다 (글자 로고)
- 핵심 기능 하나를 먼저 끝까지 (입력 → 처리 → 결과 표시). 꾸밈은 그다음. 새 기능은 API 하나, 탭 하나, 시험 하나를 한 묶음으로
- 데이터는 원본 경로를 읽는다. 복사하지 않는다 (규칙 3). 앱이 쓰는 자리 (DB 파일, 로그) 는 환경 변수나 실행 폴더 기준 상대 경로 (verify 가 자기 폴더로 복사해 돌린다)
- 자체 검증: 요구 번호마다 받아들임 시험을 먼저 쓰고 실패를 본 뒤 통과시키며 한 조각씩 만든다. 시험은 바깥 문 (화면이 보내는 API 요청을 requests 로) 에서 걸고, 화면은 스크린샷 대신 응답 본문으로 본다. 기대값은 README 의 보기와 손으로 센 작은 표본에서 잡는다 (코드와 같은 식으로 다시 계산하지 않는다). 명령은 팀장 폴더 맨 위의 `run_tests.sh` 하나 (낱 시험은 자주, 전체는 done 직전. done 때 h 가 이 폴더에서 한 번 더 돌린다). run_tests.sh 는 하나라도 실패하면 0 이 아닌 끝 코드 (set -e). 데이터는 `..` 기준 상대 경로로 읽는다
- 브라우저를 띄워 누르는 도구 (Playwright 같은 것) 와 Computer Use 는 깔지도 쓰지도 않는다. 눌러 봐야 아는 것은 사람이 미리보기에서 본다: 보고의 「검증 결과」 에 「사람 확인: 탭, 누를 것, 기대 화면」
- 보고의 「흐름」 칸에 입력 → 처리 → 저장 (상태를 쥔 곳) → 표시를 파일:함수로, 「결정」 칸에 틀과 방식의 권유, 「사례」 칸에 고친 일 (발견, 진단, 받아들임 고침 버림, 확인)
- 「피드백」 이나 「고침: F번호」 를 받으면 그 문제에서 실패하는 시험부터 만들고 고친다 (시험은 남긴다). 바꾸기 전에 기존 시험이 도는지 보고, 바꾼 곳과 확인 방법을 보고에 적는다
- 팀원이 있으면 팀장이 나눈다 (예: product_1 엔진과 API, product_2 운영자 화면, product_3 일반 화면). 공용.md 에 API 주소, 자료 꼴, 포트를 적고 팀원은 그것을 따른다. 팀장이 product/병합/ 으로 모아 돌려 본 뒤 보고한다
