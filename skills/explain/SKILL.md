# 설명.md (한 쪽)

- 재료는 다섯뿐: 요구.md, 결정.md, 코드, verify 의 보고와 검토 판정, 대화.md. 거기 없는 것은 「확인 안 됨」 으로 적는다. 기억이나 짐작으로 채우지 않는다
- 칸 여섯. 칸마다 첫 줄은 60자 안의 결론, 이어지는 줄 둘. 파일과 함수 이름, 숫자를 넣는다 (사람이 그 이름으로 코드를 찾는다)

| 칸 | 담는 것 | 어디서 |
|---|---|---|
| 핵심 선택 | 결과를 가르는 방법 하나 (알고리즘 수준, 판단을 코드와 LLM 에 나눈 경계). 더 단순한 안과 더 강한 안, 지금 수준을 고른 까닭 (담당자 말 인용), 감수한 비용 | 결정.md 결정, 대화.md |
| 흐름과 상태 | 입력 → 처리 → 저장 → 표시. 단계마다 파일:함수. 상태를 쥔 곳과 바꾸는 쪽 | 보고의 흐름 칸, 코드 |
| 구현 범위 | 요구 번호마다 됨, 안 함 (까닭), 가정. 남이 다시 돌려 볼 길 (시험 파일, 명령) | 요구.md 상태 칸, verify 보고 |
| 약점 | 가장 약한 곳 하나와 둘째. 지점 (파일:함수), 깨지는 조건, 파급, 다음 검증 | verify 검토의 빈틈, 결정.md 비용 |
| 조건 변화 | 규모 10배, 빈 값, 이상값, 동시 요청, 조건 바뀜 때 코드가 하는 일과 verify 가 잰 숫자. 안 쟀으면 「확인 안 됨」 | verify 심층 검증, 코드 |
| AI 협업 | 결정.md 사례 가운데 둘: 발견, AI 진단이나 제안, 받아들임 고침 버림과 까닭, 확인 결과. 사람이 바꾸거나 버린 것을 앞에 | 결정.md 사례 |

- 하네스 자체 (세션 구조, h, 자동 검토) 는 쓰지 않는다. 결과물만
- 「집중 product」 뒤에는 보고를 받을 때마다 바뀐 칸만 고친다. 「설명」 을 다시 받으면 전체를 다시 쓴다
- 다 쓴 뒤 스스로 점검: 코드에 없는 이름이 있나, 숫자에 출처가 있나, 「확인 안 됨」 이 셋을 넘으면 그 칸의 재료 (verify 전달문) 를 사람에게 제안한다
