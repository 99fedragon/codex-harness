# 최종 점검 (동결 전, 큰 모듈을 모은 뒤. 매 done 마다 돌지 않는다)

## 메인 (「최종 점검」 을 받으면)

- 요구.md 의 「됨」 과 팀장 보고에서 「됐다」 고 한 기능을 목록으로 verify 에 전달문 (`./h send verify 최종점검 <파일>`). 끝난 조건: 기능마다 통과와 실패, 사람 점검표의 답
- 보고가 오면 실패는 피드백.md 에 F번호로 적고, 「시험 후보」 는 product 에 전달문으로 (product 가 자기 시험으로 옮긴다)

## verify (최종 점검 전달문을 받으면)

- 판정의 근거: 전달문, 합의문, 요구.md, 대화.md. 앞뒤: 요구.md 의 「안 함」 과 「가정」 이 대화.md 보다 앞선다. 합의문이 「상태: 초안」 이면 대화의 요구로 판정하지 않는다. 같은 결과물의 자동 검토 판정이 있으면 읽고 거기서 본 것은 되풀이하지 않는다
- 1 결과물을 `심층<번호>/` 로 복사한다. 웹 서버 포트는 19000 + 번호
- 2 요구마다 상황 표 (기능, 상황, 차례, 기대): 정상, 경계 (빈 값, 0, 가장 큰 값, 한글과 특수 글자), 잘못된 입력, 하기 → 취소 → 다시 하기, 역할 바꿔 보기 (권한 없이 닿기), 새로고침이나 다시 로그인 뒤 유지, 동시 요청, 공격 입력 (스크립트 삽입, 경로와 SQL 삽입)
- 3 누른 것과 같은 요청: 화면 코드에서 단추마다 보내는 요청을 짝짓는다 (짝이 없는 단추는 빈틈). 상황마다 그 요청을 차례로 보내고 서버의 값을 다시 읽어 기대와 견준다. `심층<번호>/test_*.py` 로 남기고 다시 돌리는 명령을 적는다 (규칙 7)
- 4 브라우저를 띄워 누르지 않는다 (자동 조작). 화면에서만 보이는 것은 사람 점검표로 넘긴다
- 5 사람 점검표: 사람이 미리보기에서 눌러 볼 핵심 흐름 다섯 줄 안팎 (번호, 탭, 누를 것, 기대 화면) 을 이 탭에 내고 기다린다. 사람은 「1 통과, 3 실패: 반납 단추가 안 바뀜」 처럼 답한다
- 판정: 상황 실패, 사람 점검표 실패, 짝이 없는 단추, 무거운 빈틈 (보안 구멍, 핵심 요구 빠짐), 보고와 실제가 다름, 돌려 보지 못함 가운데 하나라도 있으면 「이상 있음」. 가벼운 빈틈은 적기만 한다
- 지킬 것: 쓰기는 `심층<번호>/` 안에서만. 결과물은 고치지 않고 알리기만 한다 (고침은 메인이 product 에 전달문으로). 끝내기 전에 서버를 끈다. 전달문의 기한 안에

보고 (`../h done 번호 <파일>`) 의 꼴: 첫 줄이 판정, 그다음 기능별 표 (기능, 상황 수, 통과, 실패와 재현 단계), 사람 점검표와 답, 짝이 없는 단추, 빈틈 (무거움과 가벼움), 보고와 다른 곳, 시험 후보 (product 의 시험으로 옮길 `심층<번호>/test_*.py` 의 상황), 다시 돌리는 명령
